# Develop Issue

ハッカソン向けに、完了条件を満たす最小限の変更をPRにする。`AGENTS.md`と`docs/development.md`を読み、関連仕様だけ参照する。

## 1. Issueを確定

- 指定Issueの本文・コメント・関連PRを取得する。新規なら重複を確認し、`.github/ISSUE_TEMPLATE/task.md`を使って起票する。
- やること・完了条件・確認方法をそろえる。不具合は再現手順を含める。小さなIssueなしの修正は起票を強制せず、依頼を完了条件にする。
- GitHub操作は利用可能なコネクタか`gh`を使う。作成結果が不明なら既存Issue・PRを確認してから再試行する。

## 2. ブランチを準備

- status、remote、現在のブランチ、worktree、既存PRを確認し、ユーザーの変更を保持する。
- ユーザー指定の起点・作業ブランチ・マージ先を優先する。未指定なら既存PR・規約を確認し、なければremoteの既定ブランチを起点・マージ先にする。起点をfetchしてから作業する。
- 新規名は`feature/{issue番号}`、Issueなしなら`feature/内容`。既存ブランチ・PRは確認して再利用する。
- 安全に作業できれば現在のcheckoutを使う。変更が混ざる場合は既存または専用worktreeで分離する。勝手なstash・変更破棄・強制checkout・履歴の書き換えはしない。

## 3. 仕様確認・実装

- Issueと関連仕様から、対象範囲・期待する動作・確認方法を短く示す。指定された承認手順がなければ依頼範囲内で進める。結果を左右する未決定事項は確認する。
- バグは再現テスト、機能は振る舞いのテストから始め、失敗を確認 → 実装 → 整理する。資料・文言だけの変更に形式的なテストを増やさない。
- スキーマ変更は`npm run codegen`で再生成し、実行時検証・関連仕様・テストを更新する。生成物を手編集しない。

## 4. 検証

- 関連テストと`npm run check`を実行する。solver変更はPython側も別途確認する。現在Pythonテスト基盤は未導入なので、ロジック追加時に必要なテストを導入する。
- UI変更はブラウザで対象操作を確認する。API変更は成功・失敗、権限変更はアクセス拒否も確認する。
- 整形は変更ファイルだけに適用する。受け入れ条件・テストを弱めてチェックを通さない。
- 差分と完了条件を照合する。未確認・失敗は明示し、成功扱いにしない。未検証のDraft PRを依頼されている場合は、その旨を記載して共有できる。

## 5. Commit・push・PR

- 今回の変更だけをstageし、差分を確認してcommitする。commit・PRタイトルは`refs #{issue番号} 内容`。Issueなしは内容のみで、架空の番号を付けない。
- 作業ブランチをpushし、既存PRを更新するか、確認済みのマージ先へ作成する。force pushはしない。
- `.github/pull_request_template.md`に変更内容・確認結果を書く。解決するIssueは本文に`Closes #123`、参照だけなら`Refs #123`。Issueを作成時点で手動closeしない。
- `gh`の複数行本文は一時ファイルと`--body-file`を使う。作成・更新結果を確認し、`attach_artifact`が利用可能ならPRをチャットに添付する。
- CIの状態を確認し、pendingと成功を区別する。今回の変更による失敗は修正する。プレビューURLは実際に得られた場合だけ返す。

## 6. 報告

変更内容、検証結果・CI状態、IssueとPRのリンク、残る制約を短く返す。途中で止まった場合は未完了の段階と再開に必要な情報を示す。マージ・本番デプロイ・本番DB変更は別途依頼がある場合に行う。
