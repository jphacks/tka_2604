# Create Issue

ハッカソンのMVPとデモを優先し、実装に着手できる小さなIssueを作る。このスキルではIssueの整理・起票までを行い、コードや仕様書の編集、ブランチ作成、commit、push、PR作成は行わない。

## 1. リポジトリと関連仕様を確認する

- `git remote -v`から対象GitHubリポジトリを確認する。対象を特定できない場合は確認する。
- `AGENTS.md`、`docs/development.md`、`.github/ISSUE_TEMPLATE/task.md`を読む。
- 依頼に関係するコードと資料だけを調べる。仕様は`docs/product.md`、構成・技術選定は`docs/architecture.md`、制約は`docs/schema.md`、検証範囲は`docs/validation-ci.md`を参照する。画面のデモは`docs/frontend.md`、DBは`docs/database.md`を必要に応じて読む。
- GitHub操作は利用可能なコネクタか`gh`を使う。アクセスできない場合は、完成原稿と失敗した段階・理由を返し、作成済みとして扱わない。

## 2. 目的・範囲・完了条件を整理する

- 依頼と調査結果から、何を変え、どの動作で完了を確認するかを具体化する。大きい依頼は、デモやMVPを前進させる単位で分割する。複数のIssue作成が依頼範囲か不明なら、分割案を示して確認する。
- リポジトリで分かる情報は先に調べ、目的・範囲・完了条件を左右する未決定事項だけをまとめて確認する。確認不要の指定がある場合は、推測で仕様を決めず`未確定事項`に残す。
- Notionは議論の記録、実装に使う合意済み仕様はリポジトリで管理する。認証・保存・API・LLM・ソルバーなどの未決定事項を勝手に確定せず、モックと接続済み機能を区別する。
- 制約に関わる場合は`apps/schema`を正本とし、生成型の手編集やハード制約の自動緩和を対応方針にしない。LLMは制約化と説明、ソルバーは計算を担当する。
- ユーザー指定の技術・対象範囲・確認方法を優先する。指定されていない期限・優先度・機能を追加しない。
- 原稿確認を求められた場合は、重複調査後にタイトル・本文・指定された担当者等を提示し、承認を待つ。指定がなければ、必要な仕様確認と重複調査を終えたら起票する。原稿だけの依頼ではGitHubに作成しない。

## 3. 重複Issueを検索する

- 対象機能・操作・現象・期待結果から複数の検索語を選び、openとclosedの両方をタイトル・本文で検索する。
- 候補の本文・状態・関連するコメントやPRを読み、目的・範囲・完了条件が同じかを確認する。
- 同じopen Issueがあれば新規作成せず、URLと一致理由を返す。既存Issueの編集・コメントは依頼された場合に行う。
- 類似Issueは新規Issueの`関連Issue`に差分とともに記載する。同じclosed Issueがある場合は、未解決・再発・追加対応かを調べ、新規作成が必要なら過去Issueとの違いを明記する。判断を左右する情報がなければ確認する。
- reopenは明示的に依頼・承認された場合に行う。重複検索できなければ起票せず、原稿と理由を返す。

## 4. テンプレートに沿って起票する

`.github/ISSUE_TEMPLATE/task.md`を使い、タイトルは`[Task] 短い概要`、本文は次の見出しで日本語にまとめる。テンプレートのfrontmatterや空のチェック項目は本文に残さない。

```markdown
## やること

対象・変更内容・目的。バグなら症状、再現手順、期待する動作も記載する。

## 完了条件

- [ ] 具体例や操作で成否を確認できる結果
```

- 必要な場合だけ`関連Issue`、`未確定事項`を追加する。
- 完了条件は実装方法だけでなく、観測できる結果と確認方法を書く。制約・ソルバーなら対象に応じて部の境界、欠落・重複、ハード制約違反などを具体化する。
- 検証範囲は`docs/validation-ci.md`に合わせる。ブラウザE2EやPythonテストが`npm run check`に含まれるとは書かない。資料・文言だけのタスクに形式的なテストを要求しない。
- assignee・ラベルはユーザーの指定やテンプレートの設定に従う。個人名やコピー元の設定を既定値として追加しない。

コネクタまたは`gh issue create --repo ... --title ... --body-file ...`で作成する。`gh`の複数行本文は一時ファイルに書き、`--body-file`で渡す。

- 作成後はタイトル・本文・URL・指定された担当者等を取得して確認する。
- timeout等で成否が不明なら、同じタイトルと直近のIssueを確認してから再試行する。既に作成済みなら再利用する。明確に未作成と確認できた場合だけ1回再試行し、それでも不明なら停止する。
- 担当者等の設定だけが失敗してもIssueを重複作成せず、作成済みURLと未設定の項目を報告する。

## 5. 結果を返す

Issue番号・タイトル・クリック可能なURLと、残る未確定事項を短く返す。既存Issueを再利用した場合は一致理由を示す。起票できなければ、コピー可能なタイトル・本文と作成できなかった理由を返す。
